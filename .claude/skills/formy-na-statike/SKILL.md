# Формы на статике

Назначение: создать форму заявки с доставкой писем и проверить её до боевого
запуска. Скилл универсален — применим к другим сайтам на других хостингах и
серверах; конкретные хостинги упоминаются только в кейсах-примерах.

Скилл — вспомогательный компонент для продуктов скилла копирования сайтов
(лендинг, полная копия); вызывается, когда в продукте появляются формы.

## Начало задачи

1. Зафиксировать терминологию сайтов: какой домен считается исходным/основным,
   какие поддомены допустимо называть кратко, прочие домены — только полным
   адресом. Проговаривать в начале задачи, чтобы не править не тот сайт.
2. Уточнить конечную цель и предложить ветки работ явно («дойдём до X, дальше
   могу сделать Y или Z — нужно ли?»). Формы — не всегда вся задача.
3. Собрать максимум информации до исполнения (принцип «план со сбором
   максимума информации»): вопросы владельцу — одним списком на этапе
   планирования; вопрос считается закрытым только с ответом или отметкой
   «не применимо / не может ответить». Открытых висяков к старту не оставлять.

## Этап 0. Инвентаризация окружения

Тип размещения — первичный фактор выбора схемы отправки, поэтому окружение
выясняется до написания обработчика. Вопросы владельцу — таблицей/списком:

| Вопрос | Зачем |
|---|---|
| Провайдер и тип размещения (виртуальный хостинг / виртуальный сервер / облако) | определяет почтовые возможности |
| Панель управления (FastPanel, ISPmanager и т. п.) | какие домены можно создать, где DNS |
| Версия PHP, расширение mbstring | под конверт и кодировки |
| DNS под нашим контролем? (где записи, кто правит) | SPF/DKIM/MX для отправителя |
| Какой почтовый сервис обслуживает домен (панель, внешний сервис, релей провайдера) | выбор mail() против SMTP |
| Какие уровни доменов можно сделать почтовыми (2-й, 3-й) | определяет схему |
| SMTP-доступ и лимиты отправки | запасная схема, объёмы |
| Существующие ящики и их назначение | From/Reply-To, копии |

Дополнительно на этапе планирования (то же правило «до работ, не примечанием
в отчёте»): URL-схема адресов сайта (слеш против .html) — фиксируется до
сборки sitemap и серверных правил; список нужных библиотек и инструментов
(установки — отдельные согласования); доступы (FTP, SMTP, панель).

Ключевое следствие из практики:
- **Виртуальный хостинг**: почтовый домен 3-го уровня скорее невозможен →
  отправка от поддомена через mail() рискованна; рабочая схема — SMTP от
  реального ящика домена 2-го уровня.
- **Виртуальный сервер с панелью** (FastPanel и аналоги): домен 3-го уровня
  может быть почтовым доменом → mail() от поддомена работает при заведённых
  DNS-записях (TXT поддомена, MX и DKIM родительского домена). Возможности
  зависят от панели и её настройки — потому инвентаризация обязательна.
- Переиспользуя шаблон с другого проекта — подтверждать почтовые условия
  заново; совпадение хостинга не гарантирует воспроизведение схемы.

## Этап 1. Выбор схемы отправки

Решающее дерево:

a) **mail()** — возможна, если почтовый домен адреса отправителя реально
   заведён: панель позволяет, SPF/DKIM/MX подтверждены записями.
b) **SMTP** — от реального ящика существующего почтового домена 2-го уровня
   (типовые порты: 25 или 2525 без шифрования, 587 STARTTLS, 465 SSL;
   у каждого провайдера уточнять).
c) **Внешний сервис / релей провайдера** — если панель почты не даёт или
   лимиты малы.

Правило отправителя: реальный адрес существующего почтового домена.
Несуществующий (noreply@…) — известный источник проблем (кейс: на одном
из проектов начальная попытка с несуществующего ящика дала сбои, рабочая
схема — после перехода на реального отправителя). В примерах кода noreply@
может встречаться как артефакт разметки — не воспроизводить как рекомендацию.

Разделение адресов: From — технический ящик отправки; Reply-To — реальный
ящик для кнопки «Ответить». Получатель — существующий ящик; копия —
второй существующий ящик (дублирование заявок страховкой).

## Этап 2. Тело письма и заголовки

- CRLF во всём письме (заголовки и тело): голые \n — сервер молча рвёт
  соединение после DATA.
- Кодировка UTF-8; отображаемое имя и тема через `=?UTF-8?B?base64?=`.
- Защита от подделки заголовков: удаление \r\n из входных полей.
- Кодирование значений полей перед вставкой в письмо.

## Этап 3. Форма и журнал-страховка

- honeypot-поле (website) — скрытое от человека, ловушка для спама.
- Обязательный чекбокс согласия на обработку персональных данных.
- Журнал-страховка `_journal`: CSV по месяцам; доступ закрыт
  `.htaccess` («Require all denied»); состав записи: дата, поля формы,
  отметка согласия, IP, браузер; срок хранения — по требованиям ПДн
  (практика: 12 месяцев). Письмо может не дойти — заявка остаётся в журнале.
- Редирект на страницу успеха выполняется независимо от исхода отправки
  письма (пользователь не видит техническую ошибку; заявка не теряется).
- Почта как часть юридического контура: адрес для запросов по ПД в политике
  (privacy@…) должен фактически существовать и получать письма.

## Этап 4. Приёмка

1. **mail-tester.com до боевого запуска** — отчёт сохранить в проект
   (как файл); цель: SPF pass, DKIM pass, отсутствие замечаний к структуре.
2. **Тестовые заявки**: из браузера и из терминала. В терминале Windows
   кириллица превращается в «??????» из-за оболочки — тело POST передавать
   файлом (`--data-binary @file`, UTF-8).
3. Письмо получателю и копии доставлено; заголовки показывают SPF/DKIM pass.
4. Запись в журнале создана; поля и отметка согласия на месте.
5. Редирект на успех отработал и при удачной, и при неудачной отправке.
6. Повторная приёмка — по полному чек-листу после каждой правки обработчика.

## Использование субагентом

Механические части делегировать субагенту: прогон чек-листа инвентаризации,
сверка журналов, повторная приёмка по критериям. В главной сессии держать
принятие решений: выбор схемы, написание обработчиков, трактовка находок.

## Кейсы-примеры (не инструкции к копированию)

- **prom-opora (kirov)**: виртуальный хостинг; ящик для домена
  3-го уровня создать нельзя; итог — SMTP-релей провайдера (порт 587)
  от реального ящика домена 2-го уровня, копия через RCPT TO; голые \n
  рвали соединение, весь конверт нормализован в CRLF.
- **Другой проект (сборка на поддоменах)**: виртуальный сервер с панелью
  управления; домены 3-го уровня сделаны почтовыми, DNS-записи заведены
  (TXT, MX, DKIM); mail() от реального отправителя поддомена,
  SPF/DKIM pass; переход с несуществующего отправителя на реальный —
  решающий шаг.
