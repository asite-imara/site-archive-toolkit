# Копирование сайтов

Назначение: универсальная методика снятия сайта и построения на его основе
продуктов. Скилл не привязан к конкретному сайту, хостингу или движку;
конкретные проекты упоминаются только в кейсах-примерах.

Скилл форм (formy-na-statike) — вспомогательный компонент: вызывается, когда
в продукте появляются формы.

## Архитектура: цепочка и продукты

Общая цепочка (шапка всех продуктов):

1. Инвентаризация ссылок, стилей, ключей, целей.
2. Архивная выгрузка (html-архив сайта).
3. Аудит сайта, ТЗ для разработчика и SEO-специалиста.

Продукты на основе цепочки:

| Продукт | Что это | Методика |
|---|---|---|
| 1. Архив | Копия, открывающаяся локально без интернета: страницы + все ресурсы + рабочие относительные ссылки. Типовые сценарии: архив перед редизайном, бэкап перед доработками, аудит структуры. | раздел «Продукт 1» ниже |
| 2. Лендинг из копии | Лёгкий лендинг: по главной с модальными заглушками, «прокладка» с переходами на основной сайт, или на основе содержания всего сайта | приложения/produkt-2-landing.md |
| 3. Полная копия | «Чистая максимально облегчённая копия»: статика html/css/js, дизайн сохранён, недостатки устранены, функционал воспроизведён; завершается планом продвижения | приложения/produkt-3-polnaya-kopiya.md |

Смешанные варианты: часть страниц — собственное содержимое лендинга
(политика, контакты, услуги, «о компании»), отдельные разделы (например,
каталог) — ссылками на основной сайт. Для смешанного варианта на этапе
планирования составляется и утверждается список разделов по каждому режиму;
по нему же проверяется приёмка.

Правила работы с цепочкой:
- конечная цель уточняется в начале задачи; владелец выбирает продукт
  и вариант внутри него;
- ветки предлагаются явно: «дойдём до архива, дальше могу сделать X
  или Y — нужно ли?»; лишние стадии не выполняются и не навязываются;
- новые вариации из практики (принципы лендинга, продукты) фиксировать
  в скилле, а не терять в диалогах.

## Начало задачи

1. Зафиксировать терминологию сайтов: какой домен считается исходным/
   основным, какие поддомены допустимо называть кратко, прочие домены —
   только полным адресом. Проговаривать в начале задачи, чтобы не править
   не тот сайт.
2. **До разведки спросить владельца об истории сайта**: на каких доменах
   и на каких движках сайт работал раньше и работает сейчас. Если владельцу
   трудно ответить — дать возможность пропустить вопрос («не знаете —
   пропустите»), не задерживать задачу. Знание истории критично для
   трактовки находок: ссылки на прежний домен владельца — это не внешние
   ссылки, а артефакты движка (WordPress хранит абсолютные ссылки в базе
   данных и не вычищает их при переносе; сбросом кеша, как в MODX, это
   не лечится). Кейс: WordPress ранее на пром-опора.рф, затем перенесён
   на catalog.prom-opora.ru; кириллические ссылки в контенте — следы
   прежнего домена, требующие переписывания на правильные адреса, а не
   включения в список «внешних».
3. Уточнить конечную цель и предложить ветки явно (см. выше).
4. Принцип «план со сбором максимума информации»: все вопросы владельцу —
   одним списком на этапе планирования; вопрос считается закрытым только
   с ответом или отметкой «не применимо / не может ответить». Открытых
   висяков к старту исполнения не оставлять; по ходу работы вопросы —
   только при фактической блокировке.

## Этап П. Планирование и инвентаризация

Выполняется до любых правок и выгрузки. Пункты, не применимые к конкретному
сайту, отмечаются «не применимо» с причиной — не молча пропускаются.

### Происхождение и окружение

| Вопрос | Зачем |
|---|---|
| Движок исходника (WordPress, MODX, Bitrix, самописный…) | какие следы движка искать при сборке; чего не воспроизвести статикой |
| Домены: основной, поддомены, стейджинг-поддомены | фильтр домена при выгрузке; ловушка base-тега |
| Хостинг, панель управления, доступы (FTP/SSH, SMTP) | деплой, почта форм |
| URL-схема адресов: слеш в конце против .html | фиксируется до сборки sitemap и серверных правил; влияет на canonical и редиректы |
| Ключи для продвижения (отдельный вопрос владельцу/сеошнику) | meta keywords часто пуст; на Bitrix ключи могут быть заполнены, но не выводиться в коде — разбор разметки даёт неполную картину |

### Содержимое (чек-лист расширенной инвентаризации)

1. **Ссылки и ключи**: карта адресов (sitemap.xml всех карт + spider-обход
   с фильтрацией параметров); чистка списка: дубли, адреса с параметрами,
   чужие домены, неактуальные. Sitemap-пробы — по расширенному набору
   адресов, а не только /sitemap.xml: sitemap.xml, sitemap.xml.gz,
   wp-sitemap.xml, sitemap_index.xml (карта YoastSEO), sitemap_index.xml.gz;
   плюс директива `Sitemap:` в robots.txt. Кейс: /sitemap.xml и
   /wp-sitemap.xml отвечали 404, инвентаризация записала «sitemap
   отсутствует», но живая карта Yoast была по /sitemap_index.xml — её
   нашёл только обходчик на этапе выгрузки, а отчёт остался с неверным
   дефектом.
2. **Внешние ссылки — две разные проверки**: адрес открывается и канал
   вообще используется компанией. Платформенная специфика: мессенджеры
   и соцсети могли перестать использоваться; домены менялись (vk.com →
   vk.ru) и редирект может отрабатывать некорректно — живой адрес с битой
   логикой перехода тоже дефект. Результат согласуется с владельцем:
   оставлять, заменять, снимать.
3. **Классы и id — три связи**: есть ли стили (какие правила), используется
   ли в js, встречается ли в разметке. Классы без стилей и js — кандидаты
   на удаление; классы из js — белый список при чистке css (кейс: чистка
   по маркеру выбросила живые стили).
4. **Существующая разметка целей** (data-атрибуты, onclick, вызовы
   счётчика) — собрать до любых правок: карта «как считалось раньше»;
   на её основе строится новая разметка и проверяется переносимость целей.
5. **Типы страниц — с примерами URL** от владельца; нет примеров — пропускать
   с отметкой, не угадывать. Структуры бывают смешанные.
6. **Иконки иконочных шрифтов**: ревизия задействованных иконок до чистки
   css; инвентаризация семейств шрифтов и их источников (кейс: FontAwesome
   с CDN, классы fa-solid не описаны в стилях).
7. **Картинки: размеры по точкам сброса** (десктоп/планшет/мобайл) — влияет
   на выбор заглушек, конвертацию и контроль веса.
8. **Движковые каталоги — полная ревизия**: проверять на иконки и картинки,
   а не только на скрипты (кейс: 4 221 файл изображений товара дособраны
   после приёмки).

## Этап В. Архивная выгрузка (общая основа)

### Выбор инструмента

Проверять до всего: wget, httrack, curl, Python (версия, наличие пакетов).
wget/httrack при наличии — рассмотреть первыми; при отсутствии — скрипт
на стандартной библиотеке Python. Установка пакетов — отдельное
согласование (граница из инструкции владельца). Для точечных проверок
достаточен curl; для рекурсии — нет.

Готовый скрипт выгрузки: `skripty/vygruzka-crawler.py` (только стандартная
библиотека; все ловушки из таблицы ниже уже учтены). Запуск:
`python vygruzka-crawler.py https://адрес-сайта/` — архив в
`./site-backup-<домен>-html`, temp в `./TMP/arhiv-<домен>-tmp` (ключи
`-o` и `--tmp` переопределяют). Возвращает mapping, failures и готовую
перезапись ссылок на относительные. Верификацию и fix-проходы скрипт
не заменяет — они отдельным шагом по методике.

### Архитектура работоспособной выгрузки

1. **Canonical ключ URL**: срезать схему, www, завершающий слеш (кроме
   корня), распаковать path (unquote). Единый ключ для дедупликации,
   mapping и редирект-алиасов.
2. **BFS-обход волнами**: очередь адресов, пакетами (практика: 48),
   пул воркеров (практика: 4–6, пауза между волнами).
3. **Классификация по Content-Type**, не по расширению: html → страница
   (парсится, ссылки в очередь); css → ресурс + парс url()/@import;
   xml+sitemap → извлечение loc; остальное → ресурс.
4. **Temp-хранилище с хэшированными именами** — исключает конфликт
   «файл против папки»; перенос в финальные пути в конце. Temp-папку
   чистить перед каждым запуском.
5. **Защита от коллизий финальных путей**: словарь занятых путей +
   суффикс-хэш; query-ресурсы получают суффикс хэша query в имени.
6. **Ограничения и повторы**: лимиты на число страниц/ресурсов и размер
   файла; повторы с бэкоффом на 429/502/503/504 — без них потерянные
   страницы выглядят как «сайт битый».
7. **Отчётность**: mapping (URL → файл), failures, сводный отчёт.

### Ловушки (главная ценность этапа)

| Ловушка | Проявление | Решение |
|---|---|---|
| Тег `<base href>` | Десятки тысяч несуществующих адресов в очереди; товары не скачиваются | Извлекать base из каждой страницы, разворачивать ссылки от него; при переписывании — удалять весь тег, регэксп на весь `<base\b[^>]*>`, а не на часть (огрызки `\" />` в сотнях файлов) |
| base на другой поддомен (стейджинг) | Страница «скачана», но ресурсы отброшены фильтром домена | Разрешать поддомены основного домена, приводить к нему; сверять число файлов против ожиданий |
| Ссылки «от корня» вместо «от файла» | На главной не заметно, на вложенных битые все ссылки | Вставленные пути — только относительные от текущего файла; обязательная программная проверка всех ссылок |
| Query в URL | Дубли путей, потеря ключей при перезаписи | Ключ включает query; при замене проверять вариант и с query, и без |
| Белый список query-параметров режет ресурсы | Ресурсы с `?ver=` (WP/плагины) не скачаны; проверка не считает их битыми, если абсолютные адреса уходят во «внешние» (кейс: каталог.prom-opora, 5 ресурсов WP, 960 ссылок) | Белый список только для страниц-обхода; ресурсы с query — докачивать отдельным fix-проходом; битость считать и по относительным, и по абсолютным адресам |
| Параметры-переключатели одной страницы | `?viewProducts=grid|list` и подобные — та же страница; краулинг их не нужен, но ссылки надо вести локально (кейс: 20 ссылок каталога) | Не краулить; в fix-проходе переписать на относительный путь к странице без параметра |
| Консоль Windows в cp1251 | Вывод лога падает на нестандартных символах (U+200C в адресах товаров); скрипт падает на print, JSON не пишется | В скриптах: `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`; приёмочный JSON писать до print или отдельным шагом |
| os.path.join с абсолютным компонентом | Ведущий слеш в относительном пути подменяет базу — `exists()` всегда ложь | Срезать ведущий слеш перед join |
| Битая разметка (сущности в атрибутах, переносы строк в адресах) | Мусорные «URL» с 200-ответом, лишние 404 | Нормализация: отсечение по кавычкам, отбрасывание адресов с пробелами/сущностями; дефекты источника воспроизводить как есть |
| Переносы строк внутри адреса | 404 при существующем файле | Нормализация пробелов в значениях, докачка по очищенному адресу |
| Ссылки на прежний домен сайта (артефакты движка) | WordPress хранит абсолютные ссылки в базе данных; после переноса домена (пром-опора.рф → catalog.prom-opora.ru) в контенте остаются самоссылки на прежний домен — сбросом кеша, как у MODX, не лечатся; выглядят как «внешние ссылки», из-за этого их ресурсы не докачиваются | Историю доменов спрашивать до разведки (см. «Начало задачи»); самоссылки на прежние домены владельца переписывать на правильные локальные адреса; файлы докачивать fix-проходом с текущего домена по тем же путям |
| `<picture>`: jpeg 404 + webp 200 | Массовые «ошибки» в отчёте при корректной копии | Сверять каждый «битый» адрес с живым сервером; пары webp/jpeg проверять вместе |
| Кодировки страниц (utf-8/cp1251) | Ломаная кириллица после перезаписи | Перезапись сохраняет исходную кодировку |
| Цепочки HTML → CSS → url()/@import | Недостающие файлы проявляются не сразу | Парсить css отдельно; srcset с дескрипторами, picture-пары, шрифты внутри css |
| Повторные запуски | Temp-состояние прошлого прогона валит новый | Очистка temp перед стартом; хэш-имена temp |
| Правки во время работающего процесса | — | Безопасны для работающего процесса; готовить к следующему запуску. Исправления — точечными fix-проходами по сохранённым файлам, не повторной выгрузкой |

Ритм: запуск в фоне, периодический просмотр прогресса; не прерывать
выгрузку ради подозрений, если очередь сокращается и страницы растут;
подозрительные паттерны (очередь только растёт, страницы стоят) —
диагностировать на живых страницах параллельно. Перед стартом — сухой
прогон/тест импорта (падение первого запуска из-за опечатки — реальный
кейс).

## Этап А. Аудит и ТЗ (завершение цепочки)

По собранному архиву и инвентаризации: недостатки исходника (битые
ресурсы, дефекты разметки, битые внешние ссылки, устаревшие каналы),
список задач для разработчика и SEO-специалиста. Политика по дефектам
источника: воспроизводить как в источнике, отдельно фиксировать как
кандидата на исправление. Продукт 1 включает этот этап целиком.

**Список дефектов источника пересобирается на этапе отчёта**, по
результатам верификации и ревизии архива — не переносится из инвентаризации.
За время выгрузки картина уточняется (находятся sitemap-файлы, всплывают
артефакты прежних доменов, часть «ошибок» опровергается кросс-проверкой),
и устаревшие записи из инвентаризации в готовом отчёте выглядят как
установленные факты (кейс: «Sitemap отсутствует» из инвентаризации ушёл
в финальный отчёт, хотя карта была найдена и скачана).

**Завершение задачи — обязательный шаг**: файл диалога записывается
в docs/sessions по правилу нейминга (dialog-тема-дата.md). Сессия без
записанного диалога считается незавершённой; при длительной задаче —
записывать вехами (этап/продукт), не откладывая до конца.

## Продукт 1. Полный html-архив

Копия открывается локально в браузере без интернета; страницы + все
ресурсы + рабочие относительные ссылки.

Верификация (без неё копия «работает» только на вид):

1. **Сверка со sitemap**: число адресов в sitemap.xml против числа
   скачанных страниц — ловит потерянные и лишние страницы.
2. **Проверка всех локальных ссылок**: каждый href/src/srcset разрешается
   относительно файла и проверяется на существование цели. Метрика
   «битых локальных ссылок» — главный интегральный показатель.
3. **Кросс-проверка с живым сервером**: каждый класс «ошибок загрузки»
   проверяется запросом к живому сайту, чтобы отличить дефект копии
   от дефекта источника.
4. **Точечные пробы**: код ответа и Content-Type выборочных страниц
   (главная, категория, товар), отсутствие `<base>`.
5. **Перепроверка архива по его содержимому**: ревизия скачанных файлов
   на нестандартные типы (xml, json, txt, gz, csv) — так находятся файлы,
   не выявленные разведкой и не учтённые в инвентаризации. Кейс: в архиве
   обнаружились sitemap-файлы, хотя инвентаризация записала «sitemap
   отсутствует».
6. **Вскрытие sitemap, попавшего в архив**: извлечь все `<loc>` из карты
   и всех дочерних карт, сверить каждый адрес с mapping и файлами архива;
   недостающее — докачать fix-проходом. Это контроль полноты spider-обхода
   и поиск страниц, о которых обходчик не узнал. Кейс: 194 адреса из шести
   карт Yoast — все оказались в архиве, обход полный.

Критерии приёмки: число страниц ≥ адресов в sitemap; 0 битых локальных
ссылок, кроме воспроизведённых дефектов источника (каждый подтверждён
на живом сервере); index.html открывается и ведёт по цепочке ссылок;
mapping полный; sitemap из архива вскрыт, все адреса закрыты.

## Продукт 2. Лендинг из копии

Резюме: сборка из архива перезапускаемым скриптом; чистка корзинного
стека и CSS с дедупликацией; выбор одного из трёх принципов (или
смешанного); webp; цели Метрики; формы — по скиллу formy-na-statike.
Полная методика: приложения/produkt-2-landing.md.

## Продукт 3. Полная копия на другом домене

Резюме: этапы 0–7 (инвентаризация → сборка → чистка движка → клиентский
каталог → CSS → Метрика и формы → приёмка и деплой); завершается планом
продвижения. Полная методика: приложения/produkt-3-polnaya-kopiya.md.

## Общая приёмка (все продукты)

- **Локальная проверка при base-теге**: если в разметке остаётся base на
  рабочий домен, локальная проверка страниц — только с перехватом запросов
  к домену (Playwright route + подмена локальными файлами), иначе ложные
  «битые» ресурсы.
- **Слайдеры и интерактив**: статический скриншот первого слайда ничего
  не доказывает — проверять пролистыванием через управление слайдером
  с снимками.
- **Чек-лист приёмки продукта** прогонять целиком после каждой правки;
  повторная приёмка — по полному чек-листу, не по дельте.

## Использование субагентом

Делегировать субагенту: прогон чек-листа инвентаризации, проверку локальных
ссылок, сверку со sitemap, повторную приёмку по критериям, сбор статистики
весов. В главной сессии держать решения: выбор инструмента, трактовку
находок (дефект копии против дефекта источника), изменения в конвейере.

## Кейсы-примеры (не инструкции к копированию)

- **Архив prom-opora (продукт 1)**: 5 070 файлов, обход ~20 минут;
  73 000 → 504 битых ссылок после правки относительности, все 504 —
  дефекты источника; ловушка base на стейджинг-поддомен.
- **Архив catalog.prom-opora (продукт 1)**: WordPress + WooCommerce,
  192 страницы, 6 733 ресурса, 467 МБ; sitemap — только по
  /sitemap_index.xml (Yoast), стандартные адреса 404 и без 301; сервер
  режет по User-Agent (браузерный UA обязателен); 53 780 ссылок, 7 битых —
  все дефекты источника; ловушки `?ver=`-ресурсов, `?viewProducts`,
  U+200C в адресе товара, cp1251-консоль; WordPress ранее работал на
  пром-опора.рф — кириллические самоссылки в контенте (4 документа и
  картинки переписаны на локальные, doc и pdf докачаны в fix-проходе).
- **Лендинг kirov (продукт 2, «прокладка»)**: HTML 242 → 158 КБ, CSS
  2,1 → 0,54 МБ, JS 22 → 4 файла, картинки 13,2 → 6,8 МБ; 133 внешних
  ссылки на основной сайт — штатная схема «прокладки» для рекламы.
- **Полная копия moskva (продукт 3)**: 459 страниц, MODX + miniShop3;
  удаление следов движка на 458 страницах; каталог на клиенте (JSON:
  цены, поиск, фильтры), корзина на localStorage, 2 533 формы на
  клиентском перехвате; CSS 1,54 → 0,82 МБ; слеш-схема адресов с 301;
  54 323 ссылки, 0 битых.
- Дефект исходника в копии (кейс): битый jpeg внутри `<picture>` —
  Chromium берёт source, галерея битая, хотя img src рабочий; исправлять
  только по решению владельца.
