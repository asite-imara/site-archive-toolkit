# Продукт 3. Полная копия на другом домене («чистая облегчённая копия»)

Приложение к скиллу kopiya-sajtov. Методика по этапам (обобщение сборки
459-страничного сайта с движком MODX + miniShop3; обобщена — без привязки
к скриптам и файлам того проекта). Вход: html-архив исходника (продукт 1)
+ утверждение целевого домена и URL-схемы. Выход: полнофункциональный сайт
на html/css/js (каталог, корзина, поиск, формы, Метрика), задеплоенный
и принятый владельцем; завершение — план продвижения.

## Решения, фиксируемые до сборки (этап П скилла)

- URL-схема: слеш в конце против .html — менять её после сборки дорого
  (десятки тысяч ссылок, canonical, sitemap, JSON); менять позднее можно
  (кейс: перевод 47 283 href + 2 533 data-url на слеш-схему), но лучше
  решить до сборки.
- Тег base: на живом исходнике base был — в сборку переносить; без base
  вложенные страницы теряют уровень при слеш-адресах.
- Корзина: localStorage + оформление одним письмом; цены и корзина — из
  одного источника (JSON).
- Поиск: клиентский по JSON-индексу (серверный поиск движка не
  воспроизводится).
- Обработчики форм: по скиллу formy-na-statike (SMTP от реального ящика,
  журнал-страховка, CSV заявок).
- Счётчик Метрики целевого домена и перечень целей — до этапа Метрики.

## Этап 0. Инвентаризация и карта страниц

- Рабочая папка сборки; инвентаризация всех html-страниц источника
  (CSV: адрес, тип, ссылки, ресурсы).
- Карта страниц по типам (разделы, карточки, информационные, служебные:
  корзина, поиск, 404); типы с примерами URL от владельца.
- Служебные страницы-заглушки движка (кейс: счётчик корзины — 11 байт)
  в сборку не включать; страницы без H1 — решить на этапе сборки.

## Этап 1. Сборка и дефекты разметки

- Копирование страниц и ресурсов из архива в структуру целевого сайта;
  img/inc/upload и деревья движка (assets/) — ревизия по чек-листу
  инвентаризации (каталоги движка проверять на картинки, не только скрипты).
- Дефекты разметки источника исправляются проходами по собранным файлам
  (битые jpeg → конвертация/заглушки/замена от владельца; места с битыми
  путями; мусор отложенной загрузки). Утраченные изображения — заглушки
  с конфигурацией соответствия и журналом; решение о видимых заглушках —
  за владельцем (наглядный показ пропавших изображений клиенту).
- Журнал правок (CSV) на каждый проход; приёмка «0 остатков» по grep.

## Этап 2. Удаление следов движка

- Удаляются полностью: inline-скрипты и теги движка, классы-маркеры
  (wp-, woocommerce-, ms3_*, formit и аналоги), пути движка (wp-content
  и т. п. → рабочие пути); переименования классов согласованно (разметка,
  css, js).
- Абсолютные ссылки на исходный домен → относительные (или на целевой
  домен — по решению о canonical).
- Текст сохранённого движкового кода (цели, идентификаторы форм) — в
  inventory для следующих этапов.
- Приёмка: grep по маркерам движка — 0 по всей сборке.

## Этап 3. Каталог на клиенте и формы

- Состав разделов каталога снимается с живого сайта (AJAX-индексы движка),
  если в архиве недостоверен.
- JSON-данные: цены, карточки, индекс поиска, атрибуты фильтра по разделам.
  Ловушка: атрибуты фильтра есть только в разметке разделов, их нет в
  разметке карточек — индекс собирается из таблиц характеристик карточек
  при сборке; цены и id извлекаются надёжно (скрытые input + блок цены).
- Клиентские скрипты: цены, корзина (localStorage, отдельный ключ
  на каждый сайт), фильтр, поиск; серверные обработчики — form.php
  и order.php по скиллу formy-na-statike (SMTP, журнал CSV, honeypot,
  whitelist formid, копия письма).
- Массовая правка форм на всех страницах (практика: 2 533 формы) —
  единый проход с журналом; приёмка чисто.
- Проверки на этом этапе — HTTP-уровня; поведенческая проверка в браузере —
  на этапе 7 перед деплоем.

## Этап 4–5. CSS и стили

- Чистка с дедупликацией (правило из produkt-2: белый список классов
  из js, визуальная сверка после каждой чистки); custom/theme css
  сокращаются кратно.
- Дубли подключений link удалять (практика: 916 дублей).
- Разделение: крупный inline-стиль → отдельный файл; объединение мелких
  файлов в common; критические стили инлайнить по типам шаблонов
  (компромисс «критические стили против preload» — решение владельца).
- **Опасность объединения файлов**: копии одного правила могут оказаться
  внутри @media, а копии верхнего уровня — нет (кейс: отступ кнопки не
  применялся на десктопе). После объединения проверять, что правила
  верхнего уровня не «уплыли» в @media.
- Аудит «потерянных селекторов» — с поправкой на артефакты CSSOM
  (см. produkt-2, раздел 3); структурных изломов быть не должно.
- Скриншотный протокол детерминированный: вьюпорт на всю высоту, без
  full_page; одни и те же страницы до/после.

## Этап 6. Метрика и формы

- Счётчик целевого домена + noscript на все страницы; JS-модуль с
  константой счётчика и целями.
- Цели: из карты существующей разметки (этап П) — формы, корзина,
  наведение и клик по телефону/email, мессенджеры, вызовы модальных
  окон (отдельные цели на разные события); перечень целей отдельным
  файлом для кабинета. Легаси-дублей не заводить.
- Перехват отправки форм клиентским скриптом: успех → цель + сообщение +
  закрытие модалки; формы реально отправляются через обработчики этапа 3.
- Сторонние сервисы (коллтрекинг и т. п.): решение владельца; кейс —
  Callibri удалён, так как привязывается к одному счётчику Метрики и
  одному аккаунту рекламы и искажает данные при кампаниях на разные сайты.

## Этап 7. Приёмка, robots/sitemap, деплой

1. robots и sitemap на целевой домен; число адресов в sitemap сверено
   с числом страниц сборки; служебные страницы исключены.
2. Полный чекер ссылок по сборке (практика: 99 994 ссылки): битые
   font-face, иконки, стейджинг-ссылки, битые srcset; восстановление
   недостающих деревьев (assets/) из архива. Остаток — дефекты источника,
   проверенные на живом сервере (класс из SKILL.md).
3. Скриншоты выборки страниц × вьюпорты — рендер верный.
4. URL-схема приведена к решению этапа П: канонические адреса, sitemap,
   серверные правила (301 на схему с явным https — за прокси Apache иначе
   редиректит на http; DirectoryIndex; ErrorDocument; guard на
   REDIRECT_STATUS; Options -Indexes).
5. Деплой — только с подтверждения владельца. Порядок: .htaccess первым,
   цепочки редиректов проверяются curl'ом на живом, затем остальные файлы.
   Журнал деплоя (файл за файлом). Скрипты деплоя собирают пути
   относительными (кейс: первая попытка целиком упала из-за абсолютных
   путей в сборе списка).
6. Поведенческий тест на хостинге: формы и заказ (записи в CSV, письма
   до получателя и копии), HTTP-коды (200/301/404), base/canonical,
   sitemap. Локальная проверка страниц при base — только с перехватом
   запросов к домену.
7. Поведенческая приёмка владельцем в браузере (корзина, фильтр, поиск,
   формы); замечания — в доработку; приёмка закрывается отчётом.
8. Вебмастер: переотправка sitemap — решение владельца (сайт не
   проиндексировался — надобности может не быть).

## План продвижения (завершение продукта 3)

По п. 1.13 продукт 3 завершается планом продвижения сайта: базовые
рекомендации по структуре, метатегам, целям аналитики и рекламным
посадочным страницам. Оформляется отдельным документом по результатам
аудита (этап А скилла).

## Типовые хвосты (не забывать)

- CSV-журналы форм/заявок пересоздать в чистом UTF-8 с BOM; тестовые
  записи удалить (по решению владельца).
- Временные скрипты конвейера: сохранять, если владелец не велел
  зачистить (они нужны для повторных прогонов и приёмки).
- Возврат base-тега в сборку — проверять отдельно: этап сборки мог его
  не перенести, а на слеш-схеме без base вложенные адреса ломаются
  (кейс: /katalog/ открывался из katalog.html в корне).
- Идемпотентность конвейера: если шаги нумеруются, некоторые шаги
  неидемпотентны — порядок конвейера обязателен и документируется
  (практика: 10 → 21 → 32 → 34 → 42 → 43 → 50 → 52).
