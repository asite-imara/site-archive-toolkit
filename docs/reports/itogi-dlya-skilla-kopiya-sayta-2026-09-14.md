# Разбор сессии для проработки навыка: полная статическая копия сайта

Дата: 2026-09-14
Основа: dialog-sessiya-kopiya-sayta-2026-09-14.md + итоги задачи в site-backup-html

## 1. Что представляет собой задача (потенциальный скилл)

Название: «Полная статическая HTML-копия сайта».
Цель: сохранить сайт целиком так, чтобы копия открывалась локально в браузере без интернета: страницы + все ресурсы + рабочие относительные ссылки.
Типовые сценарии использования у заказчика: архив перед редизайном/переносом, бэкап перед доработками, аудит структуры.

## 2. Выбор инструмента (проверка окружения до всего)

| Инструмент | Статус в сессии | Вывод |
|---|---|---|
| wget | нет | — |
| httrack | нет | — |
| curl | есть | годится для точечных проверок, не для рекурсии |
| Python 3.14 | есть | основной инструмент: стандартная библиотека, без установки пакетов |

Урок: сначала проверять наличие wget/httrack; при их отсутствии — самописный скрипт на стандартной библиотеке Python. Установку пакетов не потребовалось.

## 3. Архитектура скрипта, которая доказала работоспособность

1. **Canonical ключ URL**: scheme срезана, www срезано, завершающий слэш срезан (кроме корня), путь распакован (unquote). Единый ключ для дедупликации, mapping и редирект-алиасов.
2. **BFS-обход волнами**: очередь адресов, пакет по 48, ThreadPoolExecutor (4–6 воркеров, пауза 0,2 с). Обход завершён за ~20 минут на 5 257 запросов.
3. **Классификация по Content-Type**, а не по расширению: html → страница (парсится, ссылки ставятся в очередь), css → ресурс + парс url()/@import, xml+sitemap → извлечение <loc>, остальное → ресурс.
4. **Временное хранилище с хэшированными именами** (prov/<xx>/<hash10>.ext) — исключает конфликт «файл против папки» и повторные коллизии; перенос в финальные пути в конце.
5. **Защита от коллизий финальных путей**: словарь занятых путей + суффикс-хэш; query-ресурсы получают суффикс хэша query в имени файла.
6. **Ограничения**: MAX_PAGES 5000, MAX_ASSETS 20000, 30 МБ на файл, повторы на 429/502/503/504 с бэкоффом.
7. **Отчётность**: mapping.txt (URL → файл), failures.txt, сводный отчёт md.

## 4. Ключевые ловушки (главная ценность для скилла)

| Ловушка | Проявление | Решение |
|---|---|---|
| Тег `<base href>` | Десятки тысяч несуществующих адресов в очереди (25 тыс. вместо 4,7 тыс.); товары не скачиваются | Извлекать base из каждой страницы, разворачивать ссылки от него; из сохранённых страниц тег base удалять |
| base указывает на другой поддомен (new.prom-opora.ru) | Страница «парсится», но все ссылки отброшены фильтром домена; ресурсы не докачаны | Разрешать поддомены основного домена, приводить к основному домену; сверять число файлов против ожиданий |
| Ссылки «от корня» вместо «от файла» | На корневых страницах не заметно, на вложенных все ссылки битые (73 тыс.) | Все вставленные пути — только os.path.relpath от текущего файла; контрольная проверка всех ссылок обязательна |
| Удаление тега не целиком | Огрызок `" />` в 458 файлах | Регэксп на весь тег `(?is)<base\b[^>]*>`, а не на его часть |
| Query в URL | Дубли путей, потеря ключей при перезаписи | Ключ URL включает query; при поиске замены проверять и полный вариант с query, и без него |
| Битая разметка источника (HTML-сущности в атрибутах, &quot; в адресах) | Мусорные «URL» с 200-ответом, конфликты путей, лишние 404 | Нормализация: отсечение по кавычкам, отбрасывание адресов с пробелами/сущностями из загрузки; такие дефекты воспроизводить как есть |
| Переносы строк внутри адреса атрибута | 404 у сертификатов, при том что файл существует | Нормализация пробелов в значениях, докачка по очищенному адресу |
| `<picture>`: jpeg 404 + webp 200 | Массовые «ошибки» в отчёте, копия при этом корректна | Сверять каждый «битый» адрес с живым сервером, прежде чем считать дефектом копии; пары webp/jpeg проверять вместе |
| Временные файлы между запусками | FileExistsError на повторном запуске | Очистка temp-папки перед стартом; хэшированные имена temp |

### 4а. ModX-специфика тега base (уточнение 2026-09-19)

На сайтах, сделанных на ModX, тег base присутствует, как правило, всегда.
Следствие: относительные ссылки в разметке очень часто начинаются без
начального слеша — при архивации это порождает проблемы (см. ловушку в таблице
выше): без учёта base пути разрешаются не от корня, а от текущего файла.

Содержимое base бывает двух видов:
- «жёсткое» — домен прописан в теге явно;
- через переменную — домен тянется из настроек движка.

Во втором случае в base может оказаться поддомен и даже другой домен — следствие
несброшенного кеша (сайт в прошлом использовался на других доменах). Именно так
на prom-opora.ru в двух карточках оказался base на стейджинг new.prom-opora.ru.

Правило для скилла: до разбора разметки определить движок источника и уточнить,
использовался ли сайт на других доменах; неожиданный base считать не дефектом
разметки, а вероятным артефактом кеша настроек — проверять против истории
доменов, а не против «ожидаемого» одного домена.

## 5. Методика контроля качества (без неё копия «работает» только на вид)

1. **Сверка со sitemap**: количество адресов в sitemap.xml против числа скачанных страниц — быстро ловит потерянные/лишние страницы.
2. **Проверка всех локальных ссылок**: каждый href/src/srcset разрешается относительно файла и проверяется на существование цели. Метрика «битых локальных ссылок» — главный интегральный показатель. В сессии: 73 000 → 504 (все 504 — дефекты источника).
3. **Кросс-проверка с живым сервером**: каждый класс «ошибок загрузки» проверяется curl'ом на живом сайте, чтобы отличить дефект копии от дефекта источника.
4. **Точечные пробы**: код ответа и Content-Type выборочных страниц (главная, категория, товар), наличие `<base>`.

## 6. Ритм работы, который сработал

- Запуск в фоне + периодический просмотр прогресса (волны по 48 запросов, ~12/сек).
- Не прерывать выгрузку ради подозрений, если очередь сокращается и страницы растут; подозрительные паттерны (очередь только растёт, страницы стоят) — диагностировать на живых страницах параллельно.
- Правки скрипта во время работающего процесса не влияют на процесс — их безопасно готовить к следующему запуску.
- Исправления по итогам выгрузки делать точечными проходами по сохранённым файлам (fix-проходы), а не повторной выгрузкой: 20 минут обхода против секунд прохода.

## 7. Что вошло бы в скилл (набросок структуры)

**Имя**: site-html-backup (полная статическая копия сайта).

**Вход**: URL сайта, папка назначения, опционально — sitemap для сверки.
**Выход**: папка с копией, mapping.txt, failures.txt, отчёт md.

Этапы:
1. Проверка окружения (wget/httrack/python/curl), выбор инструмента.
2. План и ограничения (статичность копии, внешние ресурсы) — на утверждение.
3. Выгрузка: BFS с canonical-ключами, обход волнами, повторы на 5xx/429, лимиты.
4. Критичные правила: base-тег (извлечь/учесть/удалить), поддомены основного домена, относительность ссылок от файла, query-ключи, хэш-имена temp, очистка temp перед стартом.
5. Верификация: сверка со sitemap, проверка всех локальных ссылок, кросс-проверка ошибок с живым сервером.
6. Точечные fix-проходы по результатам верификации.
7. Отчёт: цифры, файлы, находки о самом сайте (они часто ценнее самой копии).

**Критерии приёмки**: число страниц ≥ адресов в sitemap; 0 битых локальных ссылок, кроме воспроизведённых дефектов источника (каждый — подтверждён на живом сервере); index.html открывается и ведёт по цепочке ссылок; mapping.txt полный.

## 8. Ошибки самой сессии (честный список для анализа)

1. Опечатка в вызове функции сохранения — падение первого запуска (ловится простым тестом импорта/сухого прогона перед стартом).
2. Коллизия «файл против папки» в temp — не была предусмотрена изначально.
3. Вставка путей «от корня» вместо «от файла» — самая дорогая ошибка, вскрылась только контрольной проверкой ссылок; главная страница маскировала дефект.
4. Собственный баг в контрольном скрипте (захват кавычек) — дал ложные ~97 тыс. битых ссылок, потрачен цикл на разбор.
5. Огрызок после удаления base — замечен только визуально при проверке index.html.
6. Первые два запуска не имели повторов на 429/503 — риск потери страниц при лимитах сервера; добавлено во время работающего процесса (влияет только на следующий запуск).

Общий вывод: основная ценность скилла — не сам скрипт выгрузки (он прямолинеен), а набор ловушек с тегом base/поддоменами/относительностью путей и обязательная двухсторонняя верификация (sitemap против обхода, копия против живого сервера).
